## M3 — OCR extraction and expiry alerts (2026-11-04)

- §10.1 certificate extraction: OCR text + the image go to the LLM (via `OcrClient`/`LlmClient`) with a versioned prompt (`ocr-extract@1`) that names the country's document types and its numeric date order (day-first for Nigeria) and forbids guessing dates. Output is validated with Zod (real calendar dates only); invalid output gets one retry with the error, then the document falls back to manual entry.
- Every call is logged in `ai_jobs` (prompt version, model, tokens, latency, cost estimate, status/error). Per-org monthly cap (`AI_MONTHLY_JOB_LIMIT`) until plans carry budgets. Prompts carry document-type codes and the subject name only.
- The draft is stored in `documents.extracted` with review hints: fields under 0.8 confidence (and a missing expiry) are highlighted; flags for name mismatch, already expired, different document type, no expiry; a suggested expiry from the issue date and the type's usual validity (never filled in automatically). Nothing becomes valid until a person confirms. The document page shows what was read and pre-fills the review form.
- Local development uses a fake extractor that returns a clearly labelled, plausible draft; tests register their own fixtures.
- `alerts-expiry` job: pg_cron runs hourly (UTC) and calls `/api/jobs/alerts-expiry` (Bearer `CRON_SECRET`) through pg_net, configured per environment in `private.job_config` (`app_url`, `cron_secret`; skipped when absent). The job picks orgs whose local time is 07:00, finds documents exactly 90/60/30/14/7/1/0 days from expiry (or the org's `settings.alert_offsets`), and claims each (document, offset, channel) in `document_alerts` before sending, so re-runs and overlaps never double-send. WhatsApp template to owners/managers with SMS fallback, plus in-app notifications.
- Notifications page and an unread badge in the app bar.
- Tests: extraction (valid, retry then success, two failures → manual, impossible date), prompt date-order wording, review hints, alert offsets; database-backed job tests (sent once across two runs, an org in another time zone alerted at its own 07:00, SMS fallback); e2e upload → AI draft with highlights → confirm → valid, with the `ai_jobs` row checked.
- Not yet: requirement-level alert offsets from the rule set (org offsets are used), and a real LLM/OCR vendor (Appendix item 7: choose after an accuracy test on real certificates).

## M5 — Offline mode and sync (2026-11-04)

- Captain screens (`/captain`) are now one offline-first page: the server sends a snapshot of today's work (vessels, routes, today's trips and manifests for the captain's vessels), the phone keeps it in IndexedDB (Dexie), and every screen reads from that store. Views (today, start a trip, trip, pending sync) switch on the phone, so moving between them never needs the network. Old `/captain/trips/...` links redirect.
- Write path: each action writes the record and an outbox op (`client_id` UUID v7) in one IndexedDB transaction, then syncs. The phone applies the same rules as the database (hard capacity limit, forward-only status, life jackets and at least one person before departure, amendments after departure), so ops that would be refused aren't queued.
- `POST /api/v1/sync` applies a batch in order; `sync_ops` records each op once per (org, client_id), so a replay returns the first outcome (`duplicate`) and creates nothing. Conflict rules: once a trip has moved on, the server's status wins (`conflict`); manifest entries are additive and become amendments after departure; anything else not allowed comes back `rejected` with its code. Departure, arrival and start times use the phone's clock when plausible (not in the future, not older than a week). `GET /api/v1/sync?org_id=` returns the snapshot.
- Sync runs on load, on reconnect, when the app returns to the front and every 30 s. Records show "Saved on phone" or "Synced"; an offline banner shows the pending count; the Pending sync screen lists waiting and refused changes (refused ones can be dismissed). Signing out wipes the phone's copy and asks first if changes haven't synced.
- PWA: Workbox service worker generated at build (`pnpm build` runs `scripts/pwa.mjs sw`), precaching the captain screens' assets; the captain page is network-first with the last good copy offline. Web manifest (`start_url /captain`, standalone) and icons. Development builds unregister any leftover worker.
- Captain routes JS: 166.5 KB gzipped (budget 200 KB). CI reports it per build (`pnpm pwa:size`) and fails over budget.
- `NEXT_DIST_DIR` lets a production build run next to a dev server locally.
- Tests: unit tests for the local rules, op validation, client-time clamping and conflict classification; a database test for the op log (own ops only, once per client_id, no edits); e2e: offline start → passengers → depart → arrive, sync on reconnect, server state checked, and the captured batches replayed with no duplicates (runs against a production build; skipped on a dev server); manifest and icons check.
- Not yet: Background Sync from the service worker (sync runs while the app is open), the §8 cache of safety thresholds and weather (M6), GPS points (M8) and tickets (M7) in the outbox, and the SMS fallback (M9).

## M6 — Safety lock (2026-11-04)

- §4.2 safety lock before every departure: a deterministic rules engine (`src/lib/safety/engine.ts`, shared by the server and the captain's phone) returns pass / warn / block with plain reasons (code, measured value, limit). Rules: weather at the origin and route midpoint over the trip window (wind, gusts, waves, rain over the limit → block; within 80% of a limit, poor visibility → warn; thunderstorm → block; no forecast or one older than 3 hours → warn "weather unknown"); night (departure before sunrise or arrival after sunset at the jetty, NOAA sun maths in the jetty's time zone) and permitted hours → block; no route → warn "location unknown"; over capacity or life jackets unchecked → block that can never be overridden; required vessel or captain documents expired (from the compliance rule set) → block.
- Thresholds: country defaults come from the published rule set (else the global baseline; conservative placeholders, not official limits). Orgs may only tighten them (`safety_thresholds`, enforced by a database trigger, error `thresholds_too_loose`). Settings → Safety page with the limits form.
- Weather: `WeatherClient` with an Open-Meteo adapter (forecast + marine; no key, `WEATHER_PROVIDER=open-meteo`) and the fake by default. `weather_cache` filled every 30 minutes by the `weather-poll` job (pg_cron → `/api/jobs/weather-poll`) for jetties and midpoints of active routes, and on demand when a check finds nothing fresh.
- Records, all append-only (UPDATE and DELETE revoked): `safety_checks` (computed and stored only by the server; people can't insert them), `safety_acknowledgements`, `safety_override_requests`, `safety_overrides` (decision with reason; requester and time copied from the request). Owners decide; managers too when `settings.manager_can_override` is on. Override requests notify deciders in-app and by WhatsApp interactive message (button replies arrive with the M9 webhook; the link works now).
- Departure gate in the database: `depart` (API, office, sync) returns 409 `safety_check_required` / `safety_unacknowledged` / `safety_blocked` unless the trip's latest check, stored in the last hour, passed, was accepted, or has an approved override.
- Endpoints: `GET|POST /api/v1/trips/:id/safety-check`, `POST /safety-checks/:id/acknowledge`, `POST /safety-checks/:id/override-request`, `GET /override-requests?org_id=`, `POST /override-requests/:id/decision`, `GET|PUT /orgs/:id/safety-thresholds`.
- Captain screens: a safety panel before Depart (run the check, accept warnings, ask for an override, see the decision). Offline (§8): the phone runs the same rules with its cached forecast and thresholds and queues a `safety.check` op; the server recomputes on sync (with the phone's weather and time when offline, its own fresh forecast when online); `safety.ack` is queued too. Asking for an override needs a connection, so a blocked trip stays blocked offline. Office: override inbox on the Safety page and the check history on each trip.
- Tests: table-driven engine tests (wind, gust, wave, rain, storm, visibility, stale weather, night, hours, capacity, life jackets, documents) and sun times; Open-Meteo parsing; phone depart rule; database tests (gate with stale / warn / block / approved override, capacity not overridable, append-only even for owners, manager permission, looser limits refused); e2e F2: limits, block, API 409, override request, approval, departure; offline and ferry flows updated for the safety step. Tests pin the server clock (`POST /api/dev/clock`, local only) and the browser clock to midday Lagos so the night rule doesn't depend on when CI runs.
- Not yet: admin editing of country defaults in the UI (drafts are editable in the database), handling WhatsApp button replies (M9), and an optional AI sentence explaining the reasons (§10.3; the template text is used).

## M7 — Ticketing and payments (2026-11-04)

- §5.5 tables: `payments`, `tickets`, `webhook_events` (unique per provider and event id), `fee_config`, `plans`, `plan_prices` (NGN and USD seeded; placeholder prices, admin-editable), `subscriptions`, `ledger_entries` (append-only, even for the service role), `org_settlement_accounts` (provider subaccount per org, for split settlement), `reconciliation_issues` (admin queue). Only the server writes payments, tickets, subscriptions and the ledger; people read their org's rows.
- Payments abstraction: `PaymentProvider` adapters for Paystack (checkout in kobo with subaccount split, verify, HMAC-SHA512 webhook signature, subaccounts, transfer recipients, transfers, refunds) and Flutterwave (major-unit conversion at the edge, verify by reference, `verif-hash` webhooks, subaccounts, refunds; transfers come with escrow in M13). `PaymentRouter` picks by `payment_provider_routes` (NG/NGN → Paystack, then Flutterwave); business code never names a provider. `PAYMENTS_MODE=live` with `PAYSTACK_SECRET_KEY` / `FLUTTERWAVE_SECRET_KEY` + `FLUTTERWAVE_WEBHOOK_HASH` uses the real adapters; otherwise fakes stand in under the real ids so routing behaves as configured. Provider coverage lists live in `src/config/payment-providers.ts`.
- Fees (`src/lib/fees.ts`): `platform_fee = round(price × ticket_fee_bps / 10000)` half to even at the minor unit; passenger bearer adds it, operator bearer deducts it from the operator's share (`settings.ticket_fee_bearer`, default passenger). Integer minor units with one currency throughout. Default `ticket_fee_bps` 250 (placeholder).
- Passenger flow (no account needed): `/book` lists trips with seats in the next two days → `/book/:trip` (seats, name, phone, live total) → provider checkout → `/tickets/:code` with a QR code (holds only the code). Seats are held for 15 minutes under a row lock on the trip (`reserve_ticket`), so online sales can't oversell. A paid ticket puts the passenger on the manifest; if the seats were gone by then, the payment is refunded and the case logged. Ticket lookup at `/tickets`. Payment status is only trusted from the provider (webhook, or verify on return), never the browser; amounts and currency are checked against what was asked.
- Webhooks at `/api/webhooks/payments/:provider`: signature checked, each event applied once (a repeat returns `duplicate` and changes nothing); a charge only moves a payment from initiated to success once.
- Agent sales: cash or bank transfer recorded on the office trip page (`POST /api/v1/trips/:id/tickets`), straight onto the manifest. Boarding: type or scan (BarcodeDetector on Android Chrome) the ticket code on the captain's trip screen (`POST /api/v1/tickets/board`); the manifest entry is marked boarded and the ticket used; a second scan is refused. Boarding by ticket needs a connection.
- Plans and subscriptions: Billing page (owners) with plans priced in the org's currency, per-vessel plans × charter vessels; pay a month by checkout; 7-day grace after the period ends, then read-only. Read-only is enforced in RLS: fleet, crew, routes, schedules and invitations can't be changed, while trips, manifests, safety checks and alerts keep working; a banner says so on every screen.
- `reconcile-payments` job (daily 03:15 UTC): verifies payments stuck in initiated, releases expired seat holds, moves lapsed subscriptions to past_due and then read_only.
- Local test checkout at `/dev/pay` (fakes only) completes the charge and delivers a signed webhook through the real handler.
- Tests: fee maths for both bearers in NGN and USD (incl. half-to-even); Paystack and Flutterwave request shapes, verify and webhook signatures; router fallback; database tests (server-only writes, ledger append-only, holds vs capacity, read-only gate vs trips/manifest/safety, reconcile job); e2e: online purchase → paid QR ticket → webhook replay changes nothing → forged webhook 401 → board by code → agent cash sale → pay a month of Ferry Basic.
- Not yet: recurring billing through the providers' plan APIs (each month is a checkout today), offline boarding by ticket, admin screens for fees, prices and the reconciliation queue, and settlement-account setup screens (rows can be added for now).

## M8 — Tracking and live map (2026-11-04)

- `trip_positions` (§5.3): GPS points from the phone of someone who runs the trip, accepted only during the voyage (from departure to 5 minutes after arrival, so offline points still land), append-only, unique per (org, client_id). Visible to the office and the trip's crew.
- Captain phone (§8): while a trip is departed, a point every 30 s from `watchPosition` (high accuracy), with the screen kept on where the browser allows (Wake Lock). Points queue in IndexedDB and upload oldest first after the outbox (`POST /api/v1/positions`, batches of up to 500; refused points are dropped). The trip screen shows "Tracking", "Tracking paused" (no fix for 90 s or screen off), or "Tracking off" (permission refused), plus points waiting.
- Owner live map (`/map`): vessels, current trip and status, last seen time and position, refreshed every 15 s (`GET /api/v1/map`). Mapbox GL JS draws the map when `NEXT_PUBLIC_MAPBOX_TOKEN` is set (loaded only on map screens, never on captain screens); without a token, positions are listed.
- Track replay on each trip page: drag through the voyage (an outline without a token, on the Mapbox map with one). `GET /api/v1/trips/:id/positions`.
- Public trip status (`/status/:trip`, linked from tickets; `GET /api/public/trips/:id`): route, vessel and operator, status, departure, expected arrival, arrival and last update time. No names, phones or positions. Refreshes every minute.
- Fixes: the default ticket fee is 1% (100 bps) per the spec, not the 2.5% seeded in M7. Cached weather is reused only if it covers the whole trip window (a forecast starting after departure gave "weather unknown"). Safety checks order by real insert time (`clock_timestamp()`), so the latest check is unambiguous.
- Tests: sampling and paused-state rules, knots; database tests (captain-only writes during the voyage, append-only, other crew can't see the track, 1% fee); e2e: depart → first point online → two points offline → upload in order on reconnect → map shows the latest and a new point within a minute → track replay → public page has no personal data.
- Not yet: background tracking with the screen off (a native wrapper is the route, §8), and Supabase Realtime for the map (polling is enough for the 60 s target).

Inbound SMS (`/api/webhooks/sms?token=`, Termii) through the same bot, replying by SMS. Vendor formats live in `src/server/integrations/messaging/inbound.ts`.
- Bot (§10.2): senders are matched by phone to their account and org; unknown numbers get only a sign-up link. Voice notes are downloaded and transcribed (`SttClient`, language hints per country from `src/config/languages.ts`: English or Nigerian Pidgin for Nigeria). Extraction uses the §10.2 system prompt (`voice-log@1`) with the org's vessels, routes with jetty aliases and open trips; output is validated with Zod (one retry), ids not in the context are dropped, and every call is logged in `ai_jobs`. Missing fields are asked one question at a time (vessel, route, passengers; amount and vessel for expenses). The bot replies with its own summary and Confirm / Edit / Cancel buttons (by SMS: reply YES / NO); nothing is saved before Confirm. Confirmed trip logs become arrived trips with their source (`whatsapp_voice`, `whatsapp_text`, `sms`), cash or transfer takings; fuel and expenses go to `expenses`.
- Urgent messages (danger, injury, capsizing, fire, missing person) create an `incidents` row and alert owners and managers at once by WhatsApp and SMS plus in-app; the sender is told to contact emergency services, which the bot does not replace.
- Certificate photos sent to the bot are stored, filed under the company as "other", read by the M3 extraction (which suggests the real type) and land in the review queue.
- SMS fallback format `TRIP 4 CMS IKD 18 27000` parsed deterministically (jetty aliases; `IKD` and `FAL` added). Number words and shorthand ("twenty-seven thousand", "27k") are understood.
- Safety override buttons from M6 now work in WhatsApp (owner, or a manager when allowed).
- Without an AI vendor, a rule-based reader stands in for the extractor locally (same schema), so the bot works in development.

## M12 — Contracts and invoicing (2026-11-04)

- Contracts: `contract_templates` (global or per org, `{{variables}}`; a short-form time charter is seeded) and `contracts`. The owner creates the contract from an accepted charter (owner and charterer names, vessel, dates, days, location, day rate, mobilisation, total, fuel and payment terms, governing country); missing terms show as "[not set]". Both sides accept in the app with their typed name; `accept_contract` records the time, IP, user agent and the text's hash, and nobody can set acceptance fields directly. The text locks once anyone has accepted (`contract_locked`). When both have accepted the charter moves to "waiting for payment" (escrow in M13). The PDF is stored in a private bucket and re-rendered with the acceptance record; links are 5-minute signed URLs.
- Invoices: `invoices` with a per-org, per-year number series (`INV-2026-0001`, drawn atomically), from a charter (days on hire × day rate + mobilisation, on/off-hire times when recorded) or manual lines (charges and discounts, part quantities). Paid amounts and reminder times are server-only (column grants).

## M13 — Escrow, commission and payouts (2026-11-04)

- Feature flag: escrow is off in production unless `ESCROW_ENABLED=on` (§11: not live until the legal structure is confirmed); on in local and staging.
- §5.5 tables: `escrow_holds` (one per escrow payment; amount, released and refunded in minor units; status held / partly released / released / refunded / disputed; release rule; short event history), `escrow_releases` (one per hold and tranche: mobilisation, hire, early release, admin release, admin refund), `payouts` (to a verified bank account, with our transfer reference so retries can't pay twice), `bank_accounts` (only the last 4 digits and the provider recipient code). Charters gain two-sided on-hire and off-hire confirmations.
- Flow (F6): after both sides accept the contract, the charterer pays the charter's value into the platform balance (provider routed by country/currency for `charter_escrow`). The confirmed payment funds the hold once (`fund_escrow`) and the charter becomes active. Both confirm on-hire (`confirm_hire`) → the mobilisation is released; both confirm off-hire → the rest. The charterer may release the rest early. Each release (`release_escrow`, locked, once per tranche) pays the owner gross − commission, where commission = the charter's `commission_bps` − `charter_inapp_discount_bps` (5% − 1% placeholder), rounded half to even (`src/lib/escrow.ts` mirrors it). Payouts go by provider transfer to the owner's verified account, or wait until one is added; transfer webhooks settle them once.
- Ledger (append-only): funding credits `escrow`; each release debits `escrow` and credits `platform_revenue` (commission) and `payee_payable` (owner's share); a paid-out transfer debits `payee_payable` (a reversal credits it back). Everything balances to the minor unit.
- Disputes: either side can dispute (`dispute_escrow`); releases freeze (`escrow_disputed`) and only platform admins resolve them — release, refund (provider refund) or split — from Admin → Escrow disputes. Holds, releases, payouts and bank accounts are audited.
- Screens: escrow panel on the charter page (pay in, confirm on-/off-hire, releases with commission and payout status, release early, dispute), Payouts (bank accounts, payouts), Admin → Escrow disputes. Endpoints: `POST /charters/:id/escrow/checkout`, `/charters/:id/on-hire`, `/charters/:id/off-hire`, `POST /escrow/:id/release`, `POST /escrow/:id/dispute`, `GET|POST /bank-accounts`, `GET /payouts`, `GET /admin/disputes`, `POST /admin/escrow/:id/resolve`.
- Tests: release split (both currencies, discount floor, nothing lost); database tests (pay → hold → two-sided on-hire → releases → payouts minus commission with the ledger balancing; repeated funding, repeated releases and people calling the release function themselves all refused; dispute freezes releases, admin split, no edits to holds or the ledger, audit rows written); service tests (a repeated payment webhook funds once, a repeated transfer webhook pays out once, only admins resolve); e2e F6 happy path with the payout reaching "Paid out".
- Not yet: release per hire period (hire is released at off-hire), payout reconciliation against provider statements, and legal sign-off (the flag stays off in production).

## M14 — AI tender-pack builder (2026-11-04)

- Tables: `tenders` (title, client, deadline, the tender text and any uploaded file, parsed result, status new / parsed / in progress / exported) and `tender_packs` (one per tender: vessels in the bid, checklist mapping, four drafted sections, review, "Submit anyway", export files). Owners and managers only; every change audited. Export results are server-only (column grants); a guard trigger makes the reviewer and "Submit anyway" always the signed-in user with the database time, and only the server's export can mark a pack exported.
- Step 1 (parse, §10.5 prompt `tender-parse@1`): the owner pastes the tender or uploads a PDF/photo (stored privately, read with OCR). Output is Zod-validated with one retry; every requirement must quote the tender (`quoteFound`, ignoring case, spacing and curly quotes) and anything that doesn't is dropped and counted. Logged to `ai_jobs`.
- Step 2 (map): requirements map to stored documents by keyword (`src/config/tender-keywords.ts`; Nigeria's NIMASA, cabotage and LASWA named in config) for the chosen vessels, crew and company: green valid, amber expires before the deadline, red missing, grey not matched. The owner can attach any document by hand; manual choices survive re-matching.
- Step 3 (draft, `tender-draft@1`): cover letter, company profile, vessel specification and HSE statement, one call each, from stored facts only (company, chosen vessels' specs, current certificates). Any figure in a draft that isn't in the facts or the tender is replaced with `[MISSING: confirm …]` (`guardDraft`), so nothing is invented. Drafts stay "needs review"; any edit resets the review.
- Step 4 (export): needs a review, no `[MISSING]` markers and no red mandatory items, unless the owner ticks "Submit anyway" (recorded and audited). Produces a merged PDF (index, sections, checklist quoting the tender with each item's status, then attached document files: PDF pages copied, photos placed one per page) and a ZIP (the PDF, each section as text, `checklist.csv`, the documents). Both stored in the private bucket (now allowing ZIP and photos, 50 MB); downloads are 5-minute signed links.
- Local stand-ins: without an AI vendor the parse lifts requirement lines from the tender itself and drafts are assembled from the facts with `[MISSING]` markers.
- Screens: Tenders (list), New tender, tender page (summary, vessels in the bid, checklist with manual attach, section editor with live marker count, review, submit anyway, export and downloads). Endpoints: `GET|POST /api/v1/tenders`, `GET /tenders/:id`, `POST /tenders/:id/parse|vessels|map|draft|section|review|submit-anyway|export`.
- Tests: unit (every checklist item from the fixture tender quotes it and invented ones are dropped; green/amber/red/grey mapping and vessels outside the bid; drafts have no unsupported figures after the guard; export rules); database tests (owners/managers only, export fields server-only, reviewer and submit-anyway can't be faked, audit row); e2e from pasted tender to exported PDF (`%PDF-`) and ZIP.
- Not yet: a live AI/OCR vendor (fakes and stand-ins until keys), DOCX export, and per-section regeneration.
